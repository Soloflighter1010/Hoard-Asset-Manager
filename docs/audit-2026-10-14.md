# Hoard repo audit, 14 October 2026

Everything in the repository was checked by machine, and everything new since the last audit (Hoard 3.3.2, which
followed `audit-2026-10-07.md`) was read: Hoard 4.0 to 4.1.1 and Hoard for Unity 0.8.0 to 0.8.2, about 7,600 lines.

**Status: every finding below is fixed in Hoard 4.1.2**, each with a test that fails without its fix.
`CHANGELOG.md` (4.1.2) says what changed for people using Hoard.

## How

1. **Checked by machine, all of it:** the 746 tests (Python, the pages in Chromium, and Hoard for Unity's core
   compiled and run with Mono); ruff and bandit over `hoard/` and `scripts/`; ESLint over both pages as they're
   served (`shared.js` included); `pip-audit` over all four locked requirement files; the app's `self-test`; the
   Unity package build (`build_vpm.py`); a search for secrets and personal details; and the workflows (every action
   pinned to a commit, permissions, and user-controlled values in `run:` steps).
2. **Read:** the new Python (`packages.py`, `needs.py`, `previous.py`, `sets.py`, `backup.py`, and what changed in
   `server.py`, `downloader.py`, `downloads.py`, `libraries.py`); the new page code (Look inside, What it needs,
   sets, Disk space's copies, backup, the tour, selection and the menus); and the new Unity code (`ZipReader.cs`,
   `PackageFile.cs`, `ImportQueue.cs`, `ProjectWatch.cs`, `Sets.cs`, `HoardWindow.cs`).
3. **Tried:** each finding was made to happen (a script, or the page in Chromium) before it was fixed. Each is
   marked **verified**.

## What the checks found

Nothing to fix. No known vulnerability in any locked dependency, and no secret or personal detail in the repository
(the one private key is the test suite's own `localhost` certificate). ESLint's four notes are names one page has
and the other doesn't, each guarded with `typeof`. Ruff's and bandit's are closures called at once, fixed URLs to
Hoard's own server, `--host` binding as asked, and MD5 for the Unity package's stable `.meta` GUIDs. The workflows
pin every action, take only the permissions they need, and pass no user-controlled value into a script.

## Findings

| # | Where | Problem |
|---|---|---|
| A1 | `hoard/web/downloads.html` `dupeRemovals`, `hoard/server.py` `/api/assets` | **Disk space, From more than one store, could delete the copy you chose to keep (verified).** A copy is removed (marked Removed, its files deleted) by its product key, which leaves numbers and (labels) out. Downloads also stacked by that key, so Booth's "Hair Pack 1" and "Hair Pack 2" showed as one product, though the Library keeps them apart. With Gumroad's "Hair Pack 1" too, **Keep Booth** listed two copies to remove and deleted all three. |
| A2 | `hoard/backup.py` `make` | **A backup made while the hidden library is locked named the hidden products (verified).** It left out their hidden mark, but listed them in the library list (name, creator, store link), the archive and removed choices, tags and sets. The wiki says it never does. |
| A3 | `hoard/previous.py` | **Previous versions of a file in a subfolder were lost track of (verified).** They're kept beside the file (`Textures/_Previous versions/...`), but only the product folder's own were listed. So they couldn't be restored, and stayed on disk when the product was deleted or moved to another library folder. |
| A4 | `hoard/packages.py` `look_inside` | **Look inside had no limit on the previews it keeps (verified).** Each preview has a size limit, but there was none on their number. A 1.2 MB package of compressed blank "previews" left 1.05 GB in the cache, and up to 40 such files are kept. |

### What was done

- **A1:** each download stacks as its own product (by its store and name, as in the Library), and the product key
  only for downloads the library doesn't list. A copy is offered for removal only when no copy you keep, and no
  download outside that product, shares its key. Where one store has two copies of a product, each says its name.
  Both changes stop the deletion on their own.
- **A2:** a backup made while locked leaves hidden products out of the library list, the store counts, the
  choices, tags and sets. Restoring such a backup keeps the hidden products' own tags, set places and choices, so it
  doesn't wipe them either.
- **A3:** previous versions are looked for beside each of the product's files, so they're listed, restored,
  deleted and moved like the rest. A subfolder with a link anywhere along it is left alone.
- **A4:** one file's previews are kept up to 64 MB (past that, the rest show their kind, and none is served), and
  the cache is held to 512 MB in all, keeping the newest. The same package now leaves 0.07 GB.

## Looked at and fine

- **Look inside** reads only names and previews, with every size checked before anything is set aside. Previews
  are served only by names it gave, from inside the cache. A link isn't followed, and every name on the page is
  escaped.
- **Backup restore** checks every setting as Settings does. It refuses a PIN hash with other scrypt costs, and a
  downloads folder that's a drive, home or Hoard's own. It won't replace a locked hidden library.
- **Sets and What it needs** leave hidden products out while the hidden library is locked, in the page and in
  the job logs.
- **Hoard for Unity** checks every size and place in a `.zip` against the file, and every unpacked file against its
  CRC. Unpacked file names can't leave their folder, links from the catalog are only https on the tool's or store's
  own site, and the import queue survives a script reload.
- **Releases:** 4.1.1 and Hoard for Unity 0.8.2 are published, the site and the VCC listing are up to date, and no
  issue or pull request is open.

## Not changed

- Hoard for Unity's `catalog.json` lists hidden products. It always has: Unity has no PIN, and the hidden library
  is a privacy screen for Hoard's own pages, as the wiki says.
- More than nine previous versions of one file within one second sort as text (`-10` before `-9`). This can't
  happen with the most Hoard keeps (5).
